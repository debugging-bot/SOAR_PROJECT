## 0. 현재 상태 진단

10단어 모델(`models/sign_model.keras`, 홀드아웃 평균 99.9%)이 이미 저장소에 있으므로, 9주차 실시간 작업은 지금 바로 시작할 수 있다.

**이미 동작하는 것**: 카메라 → 랜드마크 → 146차원 특징 → 30표본 버퍼 → LSTM → 확정 → WebSocket·MJPEG → 브라우저 표시·TTS의 전체 경로.

## 1. 목표 구조

```
[워커 스레드 — 감독(supervisor) 루프]
  ├─ CameraSource : 열기 / 읽기 / 끊기면 2초마다 재연결
  └─ RecognitionEngine.step(frame)            ← realtime.py도 같은 엔진을 사용
        Landmarker → build_feature_vector → FrameSampler
        → 손 검출 게이팅 → 빠른 예측 호출 → Confirmer
        → StepResult(status, progress, confirmed, top_id, top_conf, n_hand)

STATE (+ boot_id, seq, last_frame_t, error)
  ├─ WebSocket /ws      상태·확정 단어 (seq 기반으로 중복 없음)
  ├─ MJPEG    /video    카메라 영상
  ├─ GET      /health   상태 + stale 여부
  └─ GET      /api/labels  단어 목록 (퀵 키워드 버튼용)
```

`features.py`, `sampler.py`, `config.py`의 데이터 규격은 건드리지 않는다(조원 2 담당, 바꾸면 데이터 무효). 엔진은 이 함수들을 **호출만** 한다.

## 2. 단계별 작업

### A. 기준선 측정 — 지금 바로 (1~2일)

코드를 고치기 전에 현재 성능을 숫자로 남긴다. 그래야 나중에 "고쳐서 좋아졌다"를 증명할 수 있다.

- `python src/realtime.py`로 10단어 × 5회씩 시도
- 기록: 확정 성공 횟수, 같은 단어 중복 확정, 다른 단어로 오확정, 화면 왼쪽 위 fps
- **가만히 있기 테스트**: 5분 동안 머리 긁기, 휴대폰 보기, 옷 정리 같은 일상 동작 → 오확정 횟수
- `collect.py` 실행 중 fps와 `realtime.py` fps를 같은 PC에서 비교

**완료 기준**: 기준선 표 1장 (단어별 성공률, 오확정 수, fps 두 가지)

### B. 추론 엔진 정리 — 9주차 (`src/engine.py` 신설)

**B1. 루프를 클래스 하나로 모은다**

```python
class RecognitionEngine:
    def __init__(self, predict_fn, landmarker, threshold=CONF_THRESHOLD): ...
    def step(self, frame_bgr) -> StepResult: ...
    def reset(self): ...
```

`predict_fn`을 바깥에서 넣어 주므로, 테스트에서는 TensorFlow 없이 가짜 함수를 넣을 수 있다.

**B2. 예측 호출을 빠르게**
- `model.predict(x, verbose=0)` → `model(x, training=False).numpy()`
- 서버 시작 시 0으로 채운 입력으로 한 번 미리 호출(warm-up)해서 첫 확정이 느린 것을 막는다
- `time.perf_counter()`로 바꾸기 전후의 예측 1회 시간(ms)을 기록

**B3. 손 검출 게이팅**
- 최근 표본 10개 중 손이 잡힌 비율이 50% 미만이면 예측을 건너뛰고 `Confirmer`를 리셋, 상태는 WAIT
- 모델에 들어가는 특징은 바꾸지 않는 추론 전용 규칙이라 데이터 규격에 영향이 없다

**B4. `realtime.py`, `server.py`가 엔진을 쓰도록 교체**하고, 손 사라짐 리셋 조건을 하나로 통일한다.

**B5. `tests/smoke_test.py`에 엔진 항목 추가** (카메라·TF 없이 가짜 landmarker·가짜 예측 함수 사용)
- 손이 없으면 예측 함수가 호출되지 않는다
- 같은 단어가 높은 확신도로 계속 나오면 정확히 1번 확정된다
- 손이 사라지면 진행률이 0으로 돌아간다

**완료 기준**: smoke_test 실패 0개, 기준선 대비 fps 같거나 높음, 가만히 있기 테스트 오확정이 기준선보다 적음

### C. 서버 견고화 — 10주차 (12주차 예외 처리를 앞당겨 시작)

| 작업 | 내용 |

| C1. 워커 감독 | 루프 본문을 try/except로 감싸 예외 시 `STATE["error"]`에 기록하고 traceback 출력, 1초 뒤 재시작. 연속 실패 시 대기 시간을 늘림 |
| C2. 카메라 재연결 | `read()`가 연속 30회(약 1초) 실패하면 "카메라 연결이 끊겼습니다" 표시 → 카메라 해제 → 2초마다 `open_camera()` 재시도 → 성공하면 오류 해제 + `engine.reset()` |

### D. 시스템 통합 — 10주차

**D1. `GET /api/labels`**: `labels.json` 내용을 그대로 돌려준다. 퀵 키워드 버튼을 이 목록으로 만들면 어휘가 바뀌어도 화면과 모델이 어긋나지 않는다(조원 5와 협의).

**D2. 취소 처리** — 조원 1과 먼저 결정해야 한다.
- 선택지 (a): `labels.json` 끝에 `id 10 cancel` 추가 → 촬영 → 재학습. 기존 id를 바꾸지 않으므로 "id 변경 금지" 규칙에 어긋나지 않는다
- 선택지 (b): 화면의 '지우기' 버튼만 사용
- (a)일 경우 서버는 `cancel`이 확정되면 단어 대신 `{"type": "cancel"}` 이벤트를 보내고, 브라우저는 마지막 이력 카드를 지우고 음성은 내지 않는다

**D3. 지연시간 로깅**: 확정 시각(ms)을 서버 로그와 WS 메시지(`t_confirm`)에 넣고, 브라우저는 `speak()` 호출 시각을 콘솔에 남긴다. 11주차 측정의 보조 자료가 된다.

**D4. 확정 파라미터 실험** (9주차 임계값 합의와 함께)
- 임계값 0.75 / 0.85 / 0.90을 팀원 5명이 각자 시험하고, 조원 3의 `evaluate.py` 임계값표와 함께 근거로 제시
- **쿨다운 정책**: 지금은 확정 후 2.5초 동안 **다른 단어도** 막는다. "네 → 화장실"처럼 빠르게 이어서 하면 두 번째 단어가 사라진다. 대안: 같은 단어만 2.5초, 다른 단어는 1.0초. 가만히 있기 테스트와 연속 수어 테스트로 비교한다
- `config.py` 값 변경은 전원 합의 사항이다. 단, 확정 로직 값은 학습 데이터·모델에 영향이 없다는 점을 회의에서 함께 설명한다

**완료 기준**: 10주차 체크 "브라우저 한 화면에서 영상 + 큰 글씨 + 음성"이 다른 팀원 PC에서도 재현됨

### E. 측정과 장시간 실행 — 11~12주차

**E1. 지연시간 목표 정의를 먼저 바로잡는다.** 계획서의 "동작 시작부터 음성까지 1초 이내"는 현재 구조에서 달성할 수 없다. 창이 2초라서 동작의 대부분이 버퍼에 들어와야 모델이 확신을 갖기 때문이다. **"동작 종료부터 음성 시작까지 1초 이내"**로 바꿀 것을 제안한다.

이론값: 첫 확신 예측 후 연속 5회가 필요하므로 4간격 × 0.133초 = 0.53초, WS 전달 최대 0.08초, TTS 시작 0.1~0.3초를 더하면 약 **0.7~0.9초**다. 동작이 끝날 무렵 모델이 확신을 갖는다면 목표 안에 들어온다.

측정 방법: 휴대폰 슬로모션(240fps)으로 손과 모니터를 한 화면에 찍고 프레임 수로 계산, D3 로그로 보조한다.

**E2. 30분 연속 실행**: 1분 간격으로 메모리 사용량 기록. 목표는 증가폭 50MB 미만.

**E3. 오확정 테스트**: 가만히 있기 테스트 5분 → 오확정 0~1회.

**완료 기준**: 11주차 지연시간 표(평균/최대), 12주차 30분 메모리 기록, 오확정 기록

### F. 시연 지원 — 13주차

- 서버는 `127.0.0.1`에만 바인딩한다 (2026-11-02 결정). 시연 화면도 서버를 돌리는 같은 PC의 브라우저로 띄우며, 외부 접속 옵션은 두지 않는다
- 조원 5의 `start_demo.bat`이 `/health`로 서버 준비를 확인한 뒤 브라우저를 띄우도록 지원
- 데모 시나리오 1쪽 + 인식 실패 시 퀵 키워드 버튼으로 넘어가는 대응 문구

## 5. 리스크

- **홀드아웃 99.9%는 팀원 5명이 같은 조건에서 찍은 데이터 기준이다.** 실시간 인식률은 이보다 낮을 가능성이 높다. A단계 기준선에서 차이를 먼저 확인하고, 차이가 크면 조원 2(조명·거리 조건), 조원 3(재학습)과 바로 공유한다.
- **엔진 리팩터링 중 `realtime.py`·`server.py`가 깨질 수 있다.** B5 테스트를 먼저 만들고, 파일 하나씩 교체하며 커밋한다.
- **`index.html` 수정이 조원 5 일정에 묶인다.** 서버 쪽 변경(C4의 `boot_id`·`seq`)은 기존 브라우저 코드와 호환되게 만들어, 브라우저 수정이 늦어도 서버를 먼저 합칠 수 있게 한다.
